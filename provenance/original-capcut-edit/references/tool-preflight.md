# Automatic tool preflight and setup

| Need | Path | Rule |
|---|---|---|
| Start or resume an edit | [Run at entry](#run-at-entry) | Perform scoped setup as part of editing, without a separate IT-help request. |
| Discover and initialize tools | [Choose actual capabilities](#choose-actual-capabilities) | Inspect providers separately; initialize existing supported tools under current authority. |
| Reuse or refresh results | [Current evidence](#current-evidence) | Reuse only applicable observations; invalidate on relevant context changes. |
| Recover a familiar setup fault | [Bounded recovery](#bounded-recovery) | Use one eligible known recovery, then recheck the original operation. |
| Select executable branches | [Continue and hand off](#continue-and-hand-off) | Continue ready work; capability proof never replaces content or native acceptance. |
| Plan checks consistently | [Owned planner](#owned-planner) | Validate current observations and next actions; the helper never controls apps. |

## Run at entry

Before substantive source processing, route selection or a new executable handoff, perform this preflight automatically. Reuse the current ask, exact output/name, source classifications, existing decisions and still-applicable permissions. Do not wait for the user to name IT help, ask whether to discover an already authorized tool, repeat the interview, or turn setup into a separate user task. On resume, inspect current task evidence before doing another probe. Routine discovery, initialization and the known checks below belong to this workflow; they do not require a full incident investigation or historical chat scan.

Preserve the main edit outcome and retained requirements through setup. This step selects ready branches, not a universal gate before inventory or other independent preparation. SRT_ONLY never launches CapCut or requires native capture/control/writer/persistence. A silent task with no speech requirement does not probe hearing. For speech work, distinguish source-file availability, local decoding, candidate transcription and actual auditory input. Receiving a usable file does not establish that the current model/tool channel can hear it.

## Choose actual capabilities

1. Inspect the actual enabled tool catalog, installed skill entry for the relevant provider and the approved local-tool registry. Use bounded discovery; discovery is not installation/use authority. Resolve each provider independently. A native-disabled restriction on one browser/computer provider says nothing about a separate supported Windows provider. Never carry a denial to a different surface to bypass it: real denied targets/actions stay denied across routes.
2. Prefer structured local methods where available, then supported browser/native control as applicable. Load the selected provider's current skill/API before calls. For Windows, discover whether the installed computer-use provider is enabled; when its current documentation exposes it, initialize @oai/sky through the documented node_repl import rather than concluding that cua_repl describes every native tool. Do not hardcode plugin-version paths, invent API methods, inspect private provider internals or copy APIs into this leaf. The provider contract owns actual calls and restrictions.
3. Initialize/import/select an existing approved runtime/function yourself when needed and permitted. Record availability and initialization separately from successful operation. No install, upgrade, PATH change, service start, model download, permission change, source upload, paid processing or force flag follows from tool selection. Check registered executable/model identity before consequential use.
4. Use a small branch-relevant check: read/probe an authorized source and local decoded audio; test a supported auditory channel once if its capability is genuinely unknown; obtain actual pixels for the scoped native window; prove usable supported target control or inspect a compatible precision-preserving writer. No project write is a smoke test. A UIA tree is not pixels; ASR/model text is not hearing; a home-window screenshot or successful import is not a usable timeline, playback or save/reopen proof.
5. Use supported headless execution, otherwise proven hidden operation, otherwise the exact applicable visible approval. Existing approval is reused only within its actual target/action scope; it does not transfer from one app, project or run without evidence. Missing visible authority holds only that action. Never raise an unrelated window, type into an uncertain target or capture existing user documents. A blank owned-window control is optional diagnosis only with its own required authority; do not create one on every edit.

Bind method-specific capability facts in the task brief: current provider/implementation versions, session/toolset/audio context/runtime epoch/target, checked capability, observation and exact evidence path/hash. Let the current supported catalog select a different eligible provider when a previous one is unavailable; never erase an actual denial. Select one passing transfer method rather than probing every alternative.

Bind context to the selected branch: SRT_ONLY targetId identifies its supplied audio/file, appVersion is NOT_APPLICABLE and runtimeEpoch concerns the selected local processing context, not an unrelated CapCut window reset. toolsetHash covers relevant enabled providers. The planner conservatively refreshes the selected record after its context changes; it makes no fine-grained cache-efficiency claim.

## Current evidence

Reuse current successful or negative observations while their exact capability context and authority remain applicable. Do not replay an unchanged unsupported-audio submission or known exhausted capture failure. A negative observation for one provider does not suppress a newly discovered independent provider. Recheck only affected capabilities after a model/audio-modality, tool catalog, provider/API/runtime, client reset, app version/session, target or authorization change. Revalidate live state before a consequential native operation.

Keep capability cache validity separate from artifact acceptance: source/media/map/caption/style/native-revision changes invalidate their dependent word/onset/quiet/appearance/playback/persistence evidence even if tool setup remains usable. Old task exceptions and old human acceptance never supply new artifact proof. Store task observations and failures with the task; no private history or project path becomes a reusable operating dependency.

## Bounded recovery

Apply the first relevant permitted recovery; observe its result and retry the original failed operation once. Do not run the entire list as a ritual. Record attempts/recovery so resuming does not reset the budget. Two failures under one mechanism require a changed diagnosis, not another identical attempt.

| Current observation | Eligible routine action | Boundary and stop condition |
|---|---|---|
| Transcriber file input rejects metadata_errors | With existing authorized decoder, decode PCM and use the transcriber's documented ndarray input | No package changes; output remains candidate transcription, never hearing. |
| Console cannot represent source text | Use explicit UTF-8 output and checkpoint task data | No source rewrite or system-wide encoding change. |
| Launch reports no targetable window | Reconcile fresh apps/windows using supported APIs before another launch | No duplicate launch, blind close, guessed coordinates or force-kill. |
| Native frame capture times out | Refresh the returned target and use one documented capture retry within applicable visibility authority | Repeated/exhausted current failure holds pixels/native proof. UIA-only success does not clear it. |
| Auditory input is explicitly omitted/unsupported | Record the current channel unavailable and continue local decoding/transcription/preparation | Do not relabel ASR, loudspeaker playback or waveform energy as listening; no unchanged retry. |
| A native write may have happened | Read exact scoped target/journal/backups and reconcile first | No second writer or ordinary retry while the outcome is uncertain. |

For a new fault outside these tested routine paths, consult the appropriate functional owner internally. Technical instability still uses the installed it-help triage when triggered by shared policy; the agent handles that consultation without asking the user to invoke IT help, starting another task or opening an unchanged continuation menu. Use only a named unknown that can change the next action, bound the investigation, preserve access denials and continue independent authorized edit work. No rule can manufacture an unsupported audio/image channel. A real capability/authority boundary remains truthful and local to its dependent branch.

## Continue and hand off

Record preparation, auditory input, native pixels, native control, writer compatibility and native acceptance separately. Initialize the fastest eligible method and execute ready steps automatically. Native filesystem application retains all editor-closed, version, collision, source/store scope, shared-index precision, backup, pre-native content evidence and atomic readback requirements in assembly.md and pre-native-apply.md. A capability receipt is not approval or a substitute guard.

Before calling a new-session handoff executable, identify its first method setup/check and all known missing capabilities; the receiving session rechecks its own context. Source/runtime hash parity and helper tests are instruction/mechanical evidence only. Never promise a complete native edit because setup or unit tests pass. Once a support check passes, return to the nearest ready original edit step without asking again. If nothing required is executable, preserve the exact unlock condition; do not claim background continuation.

## Owned planner

scripts/capability_preflight.py evaluates a task-owned capcut-capability-session/v1 record and writes one new capcut-capability-plan/v1. It validates file hashes, independent provider status, context freshness, proof types, visibility/denial boundaries and bounded action selection. Use the tests as inert schema examples, not current-run evidence. The caller supplies actual supported-tool observations, performs returned eligible actions and updates the task record. The helper does not discover, initialize or control any runtime itself, authenticate evidence, hear, write a CapCut draft or certify content/native acceptance.

Run with explicit task-owned absolute input/output paths; --output must not already exist. Bind the selected plan path/hash in brief.capabilityPreflight. Keep real API observation and content/native verification separate. Invalid/missing records are not proof that a tool is unavailable; finish supported discovery or report the precise malformed/missing evidence.
