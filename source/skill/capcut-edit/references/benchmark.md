# Fair route benchmark

| Need | Path | Rule |
|---|---|---|
| Freeze comparable inputs | [Setup](#setup) | Equal brief, style and quality requirements. |
| Measure real work | [Timers](#timers) | Separate preparation, assembly and native proof. |
| Choose the supported winner | [Decision](#decision) | A faster failed draft cannot win. |

## Setup

Record source hashes/format/duration/rotation, script, speaker/latest-take rule, output format, app and tool versions, machine, actual encoding mode, one-line width and readable-size floor. Use a representative trial with repeated takes, prompter speech, non-keyframe boundary, difficult spelling and the longest caption. No installation or paid processing follows from choosing a test. Separate isolated outputs from the user's working draft.

Test two different questions separately: common reviewed edit-map assembly, and end-to-end work from raw source/script. Give every eligible route the same reference transcript; stale timings are not shared truth. Charge source-audio review/alignment and any reusable preprocessing once, visibly. A route cannot receive another route's completed decisions without disclosure. Native transcript Remove, FFmpeg segments, OpenChatCut/CLI and original-range compile remain distinct routes.

## Timers

Use actual start/end times for one-time setup, selection/alignment, assembly/encoding, CapCut import/relink/style, verification and corrections. Record wall time, active operator work and waiting separately. The meaningful total ends at the first verified editable content-and-captions checkpoint. Optional B-roll is excluded from that total. Save `templates/benchmark-run.json` as task data with inputs, versions, failures and evidence. Unavailable or unrun routes have unknown elapsed time, never an estimate presented as a measurement.

When repetition is useful, record a cold run plus comparable fresh-output repeats and disclose warm-cache/order effects. Use individual times and a median only when measured; do not add fake repetitions to satisfy a sample count.

## Decision

Apply pass/fail correctness and native persistence before speed. Include setup/rework cost when relevant, retain real failures and stop boundaries, and name evidence that could change the winner. If native proof is blocked, report preparation results and actual timing only for those layers. Never substitute repository test runtime, research elapsed or theoretical compute speed for editing time.
